## 1. MongoDB Atlas — from scratch  ⚠️ THE BLOCKER

Your old cluster `cluster0.t0xwwwe.mongodb.net` returns `NXDOMAIN`. Free M0 clusters are reclaimed
after prolonged inactivity, so it is gone and the credentials in `.env` are dead. Nothing can run
against real data until this is replaced.

### 1.1 Create the cluster

1. Go to **https://cloud.mongodb.com** and sign in (the account still exists even though the cluster
   does not — the same Google/email login should work).
2. **Create a new Project** — name it `AGENTIQ`. Keeping it separate from your other projects makes
   the network and user rules much easier to reason about.
3. **Create a Deployment → M0 (FREE)**. Confirm the card says **$0.00/month** before continuing.
4. **Provider: AWS. Region: Mumbai (ap-south-1).** Match the AWS region so latency stays low.
5. Name the cluster `agentiq`.

### 1.2 Database user

Atlas will prompt for a user during creation, or use **Database Access → Add New Database User**.

- Username: `agentiq_app`
- Password: **click Autogenerate Secure Password and copy it.** Do not invent one by hand, and do not
  reuse anything.
- Role: **Read and write to any database**.

> **Password gotcha that will waste your afternoon:** if the password contains `@ : / ? # [ ] %`
> it *must* be percent-encoded inside the connection string, or the URI parser will read it as a
> host separator and produce a baffling error. Autogenerated passwords usually avoid these, but
> check. `@` becomes `%40`, `#` becomes `%23`, `/` becomes `%2F`.

### 1.3 Network access

**Network Access → Add IP Address.**

- For local development: **Add Current IP Address**.
- **Important for later:** App Runner does not have a stable outbound IP. When you deploy in
  Phase 15 you will need either `0.0.0.0/0` (allow from anywhere) or an Atlas VPC peering /
  PrivateLink setup. For a student project `0.0.0.0/0` is acceptable **because the database user
  still requires a strong password** — but say so explicitly in the report rather than leaving it
  looking like an oversight. It is a deliberate trade-off, not an accident.

### 1.4 Get the connection string

**Database → Connect → Drivers → Node.js**. You get something like:

```
mongodb+srv://agentiq_app:<db_password>@agentiq.xxxxx.mongodb.net/?retryWrites=true&w=majority
```

Replace `<db_password>` with the real password, and **add the database name** before the `?`:

```
mongodb+srv://agentiq_app:REALPASSWORD@agentiq.xxxxx.mongodb.net/agentiq?retryWrites=true&w=majority
```

> Without `/agentiq` Mongoose connects to a database literally named `test`. Everything appears to
> work and your data ends up in the wrong place.

### 1.5 Verify

Put it in `server/.env` as `MONGO_URI=...`, then:

```bash
cd ~/Desktop/Projects/AGENTIQ && npm run dev:server
```

You want `MongoDB connected` in the log and:

```bash
curl -s http://localhost:3001/api/health | python3 -m json.tool
```

showing `"mongo": "connected"` and `"status": "ok"`.

## 3. S3 bucket

Bucket names are globally unique across all of AWS, so pick something specific.

```bash
export AWS_REGION=ap-south-1
export BUCKET=agentiq-artifacts-23ucs509

aws s3api create-bucket \
  --bucket "$BUCKET" \
  --region "$AWS_REGION" \
  --create-bucket-configuration LocationConstraint="$AWS_REGION"

# Block all public access — specs and evaluation output are never public.
aws s3api put-public-access-block --bucket "$BUCKET" \
  --public-access-block-configuration \
  BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true

# Versioning: an overwritten spec should be recoverable.
aws s3api put-bucket-versioning --bucket "$BUCKET" \
  --versioning-configuration Status=Enabled

# Encryption at rest.
aws s3api put-bucket-encryption --bucket "$BUCKET" \
  --server-side-encryption-configuration \
  '{"Rules":[{"ApplyServerSideEncryptionByDefault":{"SSEAlgorithm":"AES256"}}]}'
```

**Verify:**

```bash
aws s3api get-public-access-block --bucket "$BUCKET"   # all four true
aws s3api get-bucket-versioning   --bucket "$BUCKET"   # Status: Enabled
```

## 4. A dedicated IAM user for AGENTIQ

Your current user is `cost-intel-user` — named for a different project. Reusing it works, but a
security project that runs everything as one over-permissioned identity is undercutting its own
thesis, and an examiner may well ask. Ten minutes now buys you a clean answer.

Console → **IAM → Users → Create user** → `agentiq-app` → **Attach policies directly → Create
policy → JSON**, and paste this (replace `YOUR-BUCKET`):

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "BedrockInvokeOnly",
      "Effect": "Allow",
      "Action": ["bedrock:InvokeModel", "bedrock:InvokeModelWithResponseStream"],
      "Resource": [
        "arn:aws:bedrock:*::foundation-model/*",
        "arn:aws:bedrock:*:*:inference-profile/*"
      ]
    },
    {
      "Sid": "BedrockDiscovery",
      "Effect": "Allow",
      "Action": ["bedrock:ListFoundationModels", "bedrock:ListInferenceProfiles"],
      "Resource": "*"
    },
    {
      "Sid": "ArtifactBucketOnly",
      "Effect": "Allow",
      "Action": ["s3:PutObject", "s3:GetObject", "s3:DeleteObject", "s3:ListBucket"],
      "Resource": [
        "arn:aws:s3:::YOUR-BUCKET",
        "arn:aws:s3:::YOUR-BUCKET/*"
      ]
    }
  ]
}
```

Note what this policy does **not** grant: no `s3:*` on all buckets, no IAM, no EC2, no ability to
touch your other four buckets. That is the point, and it is a sentence worth having ready in the viva.

Then **Security credentials → Create access key → Command Line Interface**, and:

```bash
aws configure --profile agentiq
# paste the key id and secret, region ap-south-1, output json
```

**Verify it is correctly scoped — the second command should FAIL:**

```bash
AWS_PROFILE=agentiq aws s3 ls s3://agentiq-artifacts-23ucs509   # ✅ works
AWS_PROFILE=agentiq aws iam list-users                          # ❌ AccessDenied = correct
```

> **Never put these keys in `.env` or any file in this repository.** The AWS SDK reads
> `~/.aws/credentials` automatically. `.env.example` deliberately has no `AWS_ACCESS_KEY_ID` entry,
> and it should stay that way.


Expect `"mongo": "connected"` and `"status": "ok"`.

### Prove Bedrock end to end

```bash
cat > /tmp/b.json <<'EOF'
{"anthropic_version":"bedrock-2023-05-31","max_tokens":16,
 "messages":[{"role":"user","content":"Reply with the single word: ok"}]}
EOF

AWS_PROFILE=agentiq aws bedrock-runtime invoke-model \
  --region ap-south-1 \
  --model-id global.anthropic.claude-haiku-4-5-20251001-v1:0 \
  --body fileb:///tmp/b.json --cli-binary-format raw-in-base64-out \
  /tmp/out.json && python3 -m json.tool /tmp/out.json
```

> **The error you will hit if you use a bare model id:**
> `ValidationException: Invocation of model ID ... with on-demand throughput isn't supported.`
> Newer Bedrock models are only reachable through an **inference profile**, whose id carries a
> `global.` / `apac.` / `us.` prefix. List the ones you can actually use:
> ```bash
> aws bedrock list-inference-profiles --region ap-south-1 \
>   --query "inferenceProfileSummaries[?status=='ACTIVE'].inferenceProfileId" --output text
> ```
